# Архитектура веб-портала сбора экспертных позиций

## 1. Назначение документа

Документ описывает архитектуру MVP внутреннего портала «Стратегия развития
цифровых платформ. РГ Коммуникации, медиа и развлечения».

Портал должен поддерживать сквозной процесс:

`создание эксперта → приглашение → заполнение модулей → проверка и доработка → принятие → экспорт`.

Целевой горизонт экспертных предложений — 2036 год.

Этот репозиторий уже содержит независимый Godot-проект. Веб-портал следует
размещать в изолированном каталоге `portal/`, не изменяя структуру и зависимости
игры.

## 2. Границы MVP

В MVP входят:

- вход эксперта по одноразовой персональной ссылке-приглашению;
- личный кабинет с профилем, восемью назначенными модулями и прогрессом;
- формы, формируемые из YAML-описаний модулей;
- специальные повторяемые таблицы модулей 2–8;
- автоматическое и ручное сохранение черновика;
- отправка ответа администратору;
- комментарии, возврат на доработку и принятие ответа;
- создание компаний, экспертов, приглашений и назначений;
- загрузка и скачивание вложений;
- фильтрация ответов и выгрузка XLSX;
- история статусов и основных административных действий.

За границами MVP:

- самостоятельная регистрация и восстановление пароля;
- мобильное приложение;
- чат, уведомления в мессенджерах и встроенный ИИ;
- визуальный конструктор форм;
- сложная аналитика и совместное редактирование в реальном времени;
- публичный доступ к ответам.

Роль руководителя подгруппы закладывается в модель прав, но отдельный
агрегирующий интерфейс может быть реализован после обязательной части MVP.

## 3. Архитектура системы

### 3.1. Общая схема

Портал реализуется как модульное монолитное приложение:

```text
Браузер
   │ HTTPS
   ▼
Next.js
├── React-интерфейс (App Router, Server/Client Components)
├── Route Handlers / Server Actions
├── прикладные сервисы и проверка прав
├── загрузка YAML-конфигурации модулей
├── генерация XLSX
└── Prisma ORM
      │
      ▼
PostgreSQL

Вложения ──► файловое хранилище
             ├── локальный volume в разработке
             └── S3-совместимое хранилище в production
```

Модульный монолит выбран вместо отдельных frontend/backend-сервисов: он
соответствует размеру MVP, упрощает транзакции, развертывание и контроль
доступа, но сохраняет границы прикладных модулей для возможного последующего
разделения.

### 3.2. Технологии

- Next.js с App Router;
- TypeScript в строгом режиме;
- Tailwind CSS;
- PostgreSQL;
- Prisma ORM и миграции Prisma;
- Zod для проверки входящих данных и YAML;
- React Hook Form для динамических форм;
- библиотека `xlsx` для формирования выгрузок;
- S3-совместимый API для production-вложений;
- Vitest для модульных и интеграционных тестов;
- Playwright для основных сквозных сценариев;
- Docker Compose для приложения, PostgreSQL и локального S3-совместимого
  хранилища.

Точные версии зависимостей фиксируются при начале реализации и обновляются
контролируемо.

### 3.3. Прикладные подсистемы

```text
identity        приглашения, сессии, роли
directory       компании, эксперты, подгруппы
modules         загрузка и версия YAML-модулей
assignments     назначение модулей экспертам
submissions     черновики, ответы, отправка
review          комментарии, доработка, принятие
attachments     метаданные, загрузка и скачивание файлов
export          выборка и формирование XLSX
audit           история статусов и значимых действий
```

Интерфейс не обращается к Prisma напрямую. Route Handlers и Server Actions
вызывают прикладные сервисы, которые проверяют сессию, роль, принадлежность
ресурса пользователю и допустимость перехода статуса.

### 3.4. Развертывание

Для локальной разработки Docker Compose поднимает:

- `app` — Next.js;
- `db` — PostgreSQL;
- `storage` — S3-совместимое хранилище;
- именованные volumes для БД и файлов.

В production приложение запускается за TLS-терминирующим reverse proxy.
Секреты передаются через переменные окружения и не попадают в образ или
репозиторий. Миграции выполняются отдельной командой перед запуском новой
версии.

Минимальные переменные окружения:

```dotenv
DATABASE_URL=
APP_URL=
SESSION_SECRET=
INVITATION_TOKEN_PEPPER=
S3_ENDPOINT=
S3_REGION=
S3_BUCKET=
S3_ACCESS_KEY_ID=
S3_SECRET_ACCESS_KEY=
S3_FORCE_PATH_STYLE=
MAX_UPLOAD_SIZE_MB=20
```

## 4. Авторизация и модель доступа

### 4.1. Активация приглашения

1. Администратор создает пользователя и приглашение.
2. Сервер генерирует криптографически стойкий случайный токен.
3. В БД сохраняется только HMAC-хеш токена, а администратору показывается
   ссылка вида `/invite/{token}`.
4. При переходе сервер проверяет хеш, срок действия и отсутствие предыдущего
   использования.
5. В одной транзакции приглашение помечается использованным, пользователь
   активируется и создается сессия.
6. В браузер устанавливается cookie с флагами `HttpOnly`, `Secure`,
   `SameSite=Lax`.

Сырой токен не журналируется. По умолчанию приглашение действительно 14 дней.
Администратор может отозвать неиспользованное приглашение и выпустить новое.
Повторный вход выполняется по сессионной cookie; срок сессии — 30 дней с
возможностью принудительного отзыва.

### 4.2. Роли

| Действие | Эксперт | Руководитель | Администратор |
| --- | --- | --- | --- |
| Читать и редактировать свои назначения | Да | Да | Да |
| Отправлять собственный ответ | Да | Да | Да |
| Читать ответы своей подгруппы | Нет | Да | Да |
| Комментировать ответы подгруппы | Нет | Да, если включено | Да |
| Создавать компании и пользователей | Нет | Нет | Да |
| Назначать модули | Нет | Нет | Да |
| Менять статус проверки | Нет | Опционально | Да |
| Экспортировать данные | Нет | Свою подгруппу | Все данные |

Права проверяются на сервере для каждого действия. Скрытие кнопки в интерфейсе
не считается механизмом авторизации.

### 5.3. Переходы статусов

```text
NOT_STARTED ── сохранение ──► DRAFT
DRAFT ── отправка ──────────► SUBMITTED
NEEDS_REVISION ── отправка ─► SUBMITTED
SUBMITTED ── возврат ───────► NEEDS_REVISION
SUBMITTED ── принятие ──────► ACCEPTED
```

Эксперт редактирует только `NOT_STARTED`, `DRAFT` и `NEEDS_REVISION`.
`SUBMITTED` и `ACCEPTED` доступны ему только для чтения. Администратор может
переоткрыть принятый ответ отдельным явно журналируемым действием.

Проверка обязательных вопросов выполняется при отправке. Черновик разрешает
неполные и временно некорректные значения, но сохраняет только данные, которые
можно безопасно сериализовать по типу поля.

## 6. Конфигурация модулей

### 6.1. Источник истины и публикация

Исходные определения находятся в:

```text
portal/modules/
├── 01-industry.yaml
├── 02-transactions.yaml
├── 03-state-market.yaml
├── 04-architecture.yaml
├── 05-barriers.yaml
├── 06-effects.yaml
├── 07-international.yaml
└── 08-target-state.yaml
```

YAML валидируется Zod-схемой в CI и командой синхронизации. При публикации
изменившегося файла создается новая `module_version` с новым набором
`questions`; существующие назначения продолжают ссылаться на прежнюю версию.
Неопубликованную конфигурацию нельзя назначить эксперту.

Теоретические материалы хранятся в поле `theory` как Markdown. При выводе HTML
проходит санитизацию; raw HTML в Markdown запрещен.

### 6.2. Схема YAML

```yaml
slug: transactions
version: 1
order: 2
title: Модель транзакций
description: Описание назначения модуля
theory: |
  # Модель транзакций
  Методические материалы...
questions:
  - key: analysis_object
    type: group
    title: Объект анализа
    required: true
    fields:
      - key: company
        type: short_text
        title: Компания
        required: true
      - key: product
        type: short_text
        title: Продукт
  - key: participants
    type: table
    title: Участники
    required: true
    minRows: 1
    columns:
      - key: participant_type
        type: select
        title: Тип участника
        options:
          - demand
          - supply
          - intermediary
          - government
      - key: name
        type: short_text
        title: Название
      - key: role
        type: long_text
        title: Роль
```

Поддерживаемые типы:

- `short_text`, `long_text`, `number`, `scale`;
- `select`, `multi_select`;
- `table`, `group`;
- `file`, `link`.

Для `select` и `multi_select` варианты имеют стабильные машинные значения и
отдельные русские подписи. Для `scale` задаются `min`, `max` и подписи краев.
Для `table` задаются типизированные колонки и, при необходимости, минимальное и
максимальное число строк.

### 6.3. Общая структура восьми модулей

Каждый модуль содержит:

1. теоретическую рамку;
2. объект практического анализа;
3. вопросы конкретного раздела;
4. отраслевой вывод;
5. целевое состояние 2036 года.

Общие блоки 2, 4 и 5 также описываются в каждом YAML явно. На этапе подготовки
файлов они генерируются из общего шаблона, но итоговый YAML самодостаточен.
Это позволяет менять формулировки и обязательность по отдельным модулям без
условий в UI.

Специализированные структуры:

- модуль 2 — участники, макро- и микротранзакции;
- модуль 3 — роли государства и оценка эффективности;
- модуль 4 — доступ к данным, платформам и пользователям;
- модуль 5 — повторяемые карточки барьеров;
- модуль 6 — измеримые эффекты платформизации;
- модуль 7 — карточки международного присутствия;
- модуль 8 — карточки стратегических предложений.

Все они выражаются через `table` и `group`, поэтому отдельные жестко
запрограммированные страницы для модулей не требуются.

## 7. Пользовательские сценарии

### 7.1. Администратор приглашает эксперта

1. Администратор создает или выбирает компанию и подгруппу.
2. Создает карточку эксперта.
3. Назначает один или несколько опубликованных модулей.
4. Генерирует приглашение и передает ссылку эксперту вне портала.
5. При необходимости отзывает ссылку и создает новую.

### 7.2. Эксперт начинает работу

1. Эксперт открывает персональную ссылку.
2. Портал активирует приглашение и создает сессию.
3. Эксперт видит профиль и карточки назначенных модулей.
4. Открывает модуль, читает методические материалы и заполняет форму.
5. Черновик сохраняется кнопкой и автоматически после паузы ввода.
6. При конфликте версий портал не перезаписывает более свежие данные и
   предлагает обновить страницу.

### 7.3. Эксперт отправляет ответ

1. Сервер проверяет обязательные поля, таблицы, ссылки и числовые диапазоны.
2. При ошибках интерфейс показывает вопросы, требующие исправления.
3. При успехе статус становится `SUBMITTED`, а ответы — только для чтения.
4. Переход фиксируется в `status_history`.

### 7.4. Проверка и доработка

1. Администратор фильтрует ответы по компании, модулю, статусу и подгруппе.
2. Открывает ответ и оставляет общий или привязанный к вопросу комментарий.
3. Возвращает ответ на доработку с обязательной причиной либо принимает его.
4. Эксперт видит комментарии, исправляет ответ и отправляет повторно.

### 7.5. Экспорт

1. Администратор задает фильтры.
2. Сервер фиксирует момент выборки и формирует XLSX.
3. Книга содержит:
   - `Ответы` — одна строка на отправку с профилем, статусом и общими полями;
   - отдельный лист для каждого модуля;
   - отдельные листы для повторяемых таблиц, где одна строка соответствует
     одной строке ответа;
   - `Комментарии` и `История статусов`;
   - `Справочники` с расшифровкой кодов вариантов.
4. В заголовке выгрузки указываются дата, примененные фильтры и версии модулей.

## 8. API

API реализуется Route Handlers под `/api`. Все мутации проверяют сессию, роль,
CSRF-контекст и Zod-схему. Ответы об ошибках имеют единый формат:

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Проверьте обязательные поля",
    "fields": {}
  }
}
```

### 8.1. Сессия и приглашения

| Метод | Маршрут | Назначение |
| --- | --- | --- |
| `POST` | `/api/invitations` | Создать приглашение (admin) |
| `POST` | `/api/invitations/{id}/revoke` | Отозвать приглашение |
| `POST` | `/api/invitations/accept` | Активировать сырой токен |
| `POST` | `/api/session/logout` | Завершить текущую сессию |
| `GET` | `/api/me` | Получить профиль и роль |

Сырой токен передается телом `POST`, чтобы не попадать в журналы API.
Страница `/invite/{token}` сразу обменивает его на сессию и заменяет URL.

### 8.2. Справочники и назначения

| Метод | Маршрут | Назначение |
| --- | --- | --- |
| `GET/POST` | `/api/admin/companies` | Список/создание компаний |
| `GET/POST` | `/api/admin/users` | Список/создание экспертов |
| `PATCH` | `/api/admin/users/{id}` | Изменить или деактивировать |
| `GET` | `/api/modules` | Доступные пользователю модули |
| `POST` | `/api/admin/assignments` | Назначить модуль |
| `DELETE` | `/api/admin/assignments/{id}` | Снять пустое назначение |

### 8.3. Ответы

| Метод | Маршрут | Назначение |
| --- | --- | --- |
| `GET` | `/api/assignments/{id}` | Форма, ответы, статус, комментарии |
| `PUT` | `/api/assignments/{id}/draft` | Сохранить полный снимок черновика |
| `POST` | `/api/assignments/{id}/submit` | Проверить и отправить |
| `POST` | `/api/submissions/{id}/request-revision` | Вернуть на доработку |
| `POST` | `/api/submissions/{id}/accept` | Принять |
| `POST` | `/api/submissions/{id}/comments` | Добавить комментарий |
| `GET` | `/api/admin/submissions` | Фильтрованный список ответов |

Сохранение черновика передает `revision`. Обновление выполняется условно по
текущей ревизии; при несовпадении возвращается `409 CONFLICT`.

### 8.4. Файлы и экспорт

| Метод | Маршрут | Назначение |
| --- | --- | --- |
| `POST` | `/api/attachments/presign` | Разрешить загрузку файла |
| `POST` | `/api/attachments/complete` | Подтвердить загрузку и checksum |
| `GET` | `/api/attachments/{id}` | Получить временную ссылку скачивания |
| `DELETE` | `/api/attachments/{id}` | Мягко удалить свое вложение |
| `GET` | `/api/admin/exports/xlsx` | Выгрузить выбранные ответы |

Production-хранилище закрыто от публичного чтения. Перед выдачей временной
ссылки сервер повторно проверяет право на связанный ответ.

## 10. Безопасность и надежность

- серверная проверка ролей и владения объектом для каждого запроса;
- HMAC-хеши приглашений, непрозрачные серверные сессии и отзыв сессий;
- параметризованные запросы Prisma и Zod-валидация;
- защита мутаций с помощью `SameSite` cookie, проверки `Origin` и CSRF-токена;
- санитизация Markdown и запрет небезопасного HTML;
- allowlist расширений/MIME, ограничение размера и количества вложений;
- антивирусная проверка вложений перед доступностью в production;
- закрытое файловое хранилище и короткоживущие ссылки на скачивание;
- rate limit для активации приглашений, загрузок и административных мутаций;
- отсутствие персональных данных и токенов в прикладных логах;
- транзакции БД для активации, отправки и смены статуса;
- optimistic locking черновиков;
- ежедневные резервные копии PostgreSQL и проверяемое восстановление;
- индексы по статусу, модулю, компании, подгруппе и времени обновления.

Для MVP `status_history` обеспечивает предметный аудит переходов. Если заказчику
нужен полный юридически значимый аудит всех изменений полей, перед production
потребуется отдельный append-only `audit_log` и политика хранения.

## 11. Тестирование

### Модульные тесты

- валидация каждого типа вопроса;
- допустимые переходы статусов;
- права ролей;
- преобразование динамических ответов в строки XLSX;
- парсинг и версионирование YAML.

### Интеграционные тесты

- одноразовая активация и отзыв приглашения;
- создание назначения и черновика;
- транзакционная отправка;
- конфликт ревизий;
- возврат, повторная отправка и принятие;
- недоступность чужих ответов и вложений;
- фильтры административного списка.

### Сквозные тесты

- вертикальный сценарий этапа 2;
- заполнение повторяемой таблицы;
- обязательная валидация при отправке;
- комментарий и цикл доработки;
- выгрузка и проверка структуры XLSX.

Каждый этап завершается линтингом, проверкой типов, тестами и сборкой
production-образа.

## 13. Потенциальные риски

| Риск | Последствие | Снижение риска |
| --- | --- | --- |
| Формулировки вопросов меняются во время сбора | Ответы перестают соответствовать форме | Версии модулей и фиксация версии в назначении |
| Не определена окончательная методика модулей | Переделка UI и экспорта | Универсальная типизированная YAML-схема, раннее согласование файлов |
| Сложные таблицы неудобны на узком экране | Ошибки заполнения | Desktop-first интерфейс, построчное редактирование и проверка UX |
| Потеря черновика или параллельные вкладки | Перезапись экспертной работы | Автосохранение, индикатор состояния, revision/optimistic locking |
| Утечка персональной ссылки | Несанкционированный вход | Одноразовый короткоживущий токен, отзыв, аудит, защищенная передача |
| Вредоносные или слишком большие файлы | Риск безопасности и затрат | Allowlist, лимиты, checksum, антивирус и закрытое хранилище |
| JSONB усложняет аналитические запросы | Медленные и хрупкие выгрузки | Нормализованные метаданные, стабильные ключи и специальный слой экспорта |
| XLSX с повторяемыми таблицами трудно читать | Ручная доработка выгрузки | Отдельные листы, стабильные ID строк, справочник и ранний образец экспорта |
| Нет канала доставки приглашений | Эксперт не получает доступ | В MVP явно назначить владельца безопасной рассылки ссылок |
| Смешение портала с игровым проектом | Конфликты зависимостей и CI | Изолированный `portal/`, отдельные команды, Dockerfile и workflow |
| Роль руководителя не определена | Ошибочные права доступа | Согласовать матрицу прав до этапа 3, по умолчанию только чтение подгруппы |
| Нет требований по хранению ПДн | Юридические и эксплуатационные риски | До production определить основание обработки, сроки удаления и размещение |

## 14. Вопросы для утверждения перед реализацией

1. Должны ли все восемь модулей назначаться каждому эксперту автоматически или
   администратор выбирает их вручную?
2. Нужна ли роль руководителя подгруппы в обязательном MVP и может ли она
   принимать ответы?
3. Как администратор передает приглашения: вручную, через корпоративную почту
   или требуется отправка email самим порталом?
4. Где будет размещен production и допустимо ли S3-совместимое хранилище?
5. Какие типы и максимальные размеры файлов разрешены, требуется ли
   антивирусная проверка?
6. Каковы сроки хранения ответов, вложений, журналов и персональных данных?
7. Требуется ли полная история изменений содержимого ответа или достаточно
   истории статусов и времени последнего изменения?
8. Можно ли менять назначенную версию модуля до начала заполнения и кто
   принимает решение о миграции черновика?
9. Должны ли комментарии быть видны только автору ответа или всем экспертам
   той же компании/подгруппы?
10. Утвержден ли предложенный формат XLSX, особенно отдельные листы для
    повторяемых таблиц?

До получения ответов этап 2 может использовать безопасные значения по
умолчанию, описанные в документе, но решения о персональных данных, production
и сроках хранения должны быть приняты до ввода портала в эксплуатацию.
