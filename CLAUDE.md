# Снабжение фронта

Пошаговая игра на одной карте. Игрок — начальник снабжения: у него несколько грузовиков
и четыре роты на фронте, которым нужны топливо, боеприпасы и продовольствие. Каждый ход
он решает, кому, что и какой дорогой везти. Сеттинг вымышленный. Название рабочее.

- Правила и рамки первой версии: `docs/design.md`. Одобрены владельцем.
- Игра делается с нуля в ветке `claude/new-game`.

Старая игра ZombieGame лежит в ветке `main` как архив. Она не является основой новой:
ничего оттуда не переносить без прямого указания владельца.

## Стек

- Godot 4.7.2, GDScript, рендерер `gl_compatibility`, окно 1280×720.
- Бинарник: `/usr/local/bin/godot-4.7.2`. Команда `godot` в PATH — старая 4.6.1, её не использовать.
- Аддонов нет. README.md и AGENTS.md нет.

## Структура

- `scripts/sim/` — правила игры без узлов и отрисовки: `supply_game.gd` (состояние и ход),
  `supply_map.gd` (карта), `supply_rules.gd` (все числа баланса), `supply_bots.gd`
  (автоматические игроки).
- `scripts/ui/` — экран: `supply_screen.gd` (панели и приказы), `supply_map_view.gd`
  (карта, рисуется кодом), `supply_text.gd` (все тексты для игрока).
- `scenes/supply.tscn` — главная сцена; интерфейс собирается кодом.
- `scripts/dev/screenshot_hook.gd` — автозагрузка: сохраняет кадр, если задан `SHOT_PATH`.
- `tests/` — `test_case.gd` (базовый класс), `run_all.gd` (раннер), тесты `test_*.gd`.
- `tools/` — `run_tests.sh`, `godot.sh` (headless-запуск), `balance.gd` (прогон партий).
- `.tools/` — локальные рабочие файлы, в git не попадают.
- Файлы `*.gd.uid` коммитятся вместе со скриптами.

Правило: игровая логика живёт только в `scripts/sim/` и проверяется тестами без экрана.
Экран лишь показывает состояние и передаёт приказы.

## Проверки

```bash
./tools/run_tests.sh
```

Скрипт делает headless-импорт, запускает все тесты и возвращает 0, только если все тесты
прошли и Godot не напечатал ошибок. Новый тест: файл `tests/test_<имя>.gd`,
`extends TestCase`, методы `test_*`, проверки через `check()` и `check_eq()`.

Скриншот запущенной игры (вместо `<корень>` — абсолютный путь к worktree):

```bash
/usr/local/bin/claude-godot-shot <корень> <корень>/.tools/shot.png 60
```

Запускатель работает вне песочницы и принимает только эти три аргумента; последний —
число кадров до выхода. Получив PNG, открыть его и посмотреть глазами. Чтобы снять
нужное состояние игры, положить сценарий в `.tools/shot_setup.gd` (см. комментарий
в `scripts/dev/screenshot_hook.gd`).

Баланс после изменения правил или чисел:

```bash
tools/godot.sh --script res://tools/balance.gd -- 1000
```

Цели по долям побед автоматических игроков записаны в `docs/design.md`.

## Git

- Работать только в своём worktree и только в ветках `claude/*`. Ветку `main` не трогать.
- Без force push. Не удалять репозитории, ветки и чужие worktree.
- Обычные `git fetch` и `git push` из песочницы не работают. Только через шлюз,
  каждая команда отдельным вызовом, без `cd`, `timeout`, `env`, `&&` и других обёрток:
  - `/usr/local/bin/claude-zombiegame-git fetch` — в начале работы;
  - `/usr/local/bin/claude-zombiegame-git push` — после коммита законченного и проверенного этапа;
  - `/usr/local/bin/claude-zombiegame-git ls-remote` — проверить состояние GitHub.
- В коммит добавлять файлы поимённо, без `git add -A`: в корне видны служебные
  файлы песочницы, которые коммитить нельзя.

## Запрещено

- `sudo`, `systemctl`, `docker`.
- Деплой куда бы то ни было.
- `ssh`, `scp`, `rsync`.
- Изменение VPN и системных настроек сервера.
- Чтение `.env` и любых секретов (ключи, токены, каталог `~/.ssh`).

Если нужно что-то системное, написать заявку владельцу: он передаст её администратору.

## Дизайн и содержание

- Не переносить механики, лор и решения из других игр без прямого указания владельца.
- Крупные изменения геймплея и архитектуры сначала предлагать владельцу и ждать
  одобрения, а не вносить сразу.
- Не выдумывать факты о проекте: если чего-то нет в коде или `docs/`, так и писать.

## Субагенты

Роли описаны в `.claude/agents/`. Их предложения — гипотезы до одобрения владельца.
Код меняют только `gameplay-engineer` и `godot-architect`, и только в рамках
утверждённой задачи. Остальные анализируют и предлагают.
